# Manual Deployment

This procedure starts after a compatible `lumend` binary is available. It
covers node deployment and validator operations owned by validator-kit without
duplicating the blockchain source-build procedure.

## 1. Obtain and verify `lumend`

Validator-kit defines the current fresh-node release per network in
`networks/<network>/release.env`. Inspect `LUMEND_VERSION` before selecting a
binary. Operators may obtain that release through the verified installer, or build
`lumend` using the instructions maintained by the
[Lumen blockchain repository](https://github.com/network-lumen/blockchain).
Do not use a binary from an unverified source.

Verify the supplied executable before continuing:

```bash
export VALIDATOR_KIT_DIR="/path/to/validator-kit"
export NETWORK="mainnet"
source "$VALIDATOR_KIT_DIR/networks/$NETWORK/release.env"
printf 'Required lumend: %s\n' "$LUMEND_VERSION"
export LUMEND="/absolute/path/to/lumend"
[[ -x "$LUMEND" ]]
"$LUMEND" version
```

The reported version must match the normalized `LUMEND_VERSION` for the
selected network. Keep the exact binary path for the service configuration.

## 2. Initialize the node home

Run the node as a dedicated unprivileged user. Set `LUMEN_HOME` to a
persistent path owned by that user; `/root` is not a required or recommended
location.

```bash
export LUMEN_HOME="${LUMEN_HOME:-$HOME/.lumen}"
export CHAIN_ID="lumen"
"$LUMEND" init "${MONIKER:-lumen-validator}" --chain-id "$CHAIN_ID" --home "$LUMEN_HOME"
cp "$VALIDATOR_KIT_DIR/networks/$NETWORK/genesis.json" "$LUMEN_HOME/config/genesis.json"
```

The network directory is the source of truth for validator-kit-maintained
genesis, peers, seeds, and metadata. Verify the selected genesis chain ID
before starting the node.

## 3. Configure the node manually

Start from the files generated by `lumend init`. Use
[`config/validator/`](../../config/validator/) as the authoritative reference,
then edit the generated files so the operator understands each setting.

In `app.toml`, set `minimum-gas-prices = "0ulmn"`, keep `[api] enable = false`,
and keep gRPC enabled on `localhost:9090`. The profile also enables gRPC-Web
on its local API address; do not expose these interfaces without explicit
firewall, authentication, rate-limit, and TLS controls.

In `config.toml`, the validator profile uses:

```toml
[rpc]
laddr = "tcp://127.0.0.1:26657"

[p2p]
laddr = "tcp://0.0.0.0:26656"
pex = false
seed_mode = false

[tx_index]
indexer = "kv"

[instrumentation]
prometheus = true
prometheus_listen_addr = "0.0.0.0:26660"
```

Set `seeds` and `persistent_peers` from the selected network files. The P2P
port may be reachable from the network; RPC and metrics require deliberate
firewall rules. In `client.toml`, set `chain-id = "lumen"`,
`node = "tcp://localhost:26657"`. The reference profile currently sets
`keyring-backend = "os"`; if using the documented encrypted `file` backend,
change that value to `file` or provide the explicit CLI flag shown below.
Never use the `test` backend on a production host.

```bash
SEEDS="$(awk 'NF { gsub(/[[:space:]]+/,""); printf "%s%s", sep, $0; sep="," }' "$VALIDATOR_KIT_DIR/networks/$NETWORK/seeds.txt")"
PEERS="$(awk 'NF { gsub(/[[:space:]]+/,""); printf "%s%s", sep, $0; sep="," }' "$VALIDATOR_KIT_DIR/networks/$NETWORK/peers.txt")"
sed -i "s|^seeds *=.*|seeds = \"$SEEDS\"|; s|^persistent_peers *=.*|persistent_peers = \"$PEERS\"|" \
  "$LUMEN_HOME/config/config.toml"
```

Compare the completed files with `config/validator/` before proceeding.

## 4. Configure state sync manually

Select two trusted RPC endpoints. Verify chain ID and that both endpoints are
caught up, choose a recent trust height, and obtain the matching block hash.

```bash
export RPC_URL="https://trusted-rpc-1.example:26657"
export RPC_URL_2="https://trusted-rpc-2.example:26657"
STATUS="$(curl -fsS "$RPC_URL/status")"
STATUS_2="$(curl -fsS "$RPC_URL_2/status")"
[[ "$(jq -r '.result.node_info.network' <<< "$STATUS")" == "$CHAIN_ID" ]]
[[ "$(jq -r '.result.node_info.network' <<< "$STATUS_2")" == "$CHAIN_ID" ]]
[[ "$(jq -r '.result.sync_info.catching_up' <<< "$STATUS")" == "false" ]]
[[ "$(jq -r '.result.sync_info.catching_up' <<< "$STATUS_2")" == "false" ]]
LATEST_HEIGHT="$(jq -r '.result.sync_info.latest_block_height' <<< "$STATUS")"
TRUST_HEIGHT=$((LATEST_HEIGHT - 100))
TRUST_HASH="$(curl -fsS "$RPC_URL/block?height=$TRUST_HEIGHT" | jq -r '.result.block_id.hash')"
```

Confirm the height and hash independently, then set the `[statesync]` values
in `config.toml` before the first start:

```bash
sed -i \
  -e 's|^enable *=.*|enable = true|' \
  -e "s|^rpc_servers *=.*|rpc_servers = \"$RPC_URL,$RPC_URL_2\"|" \
  -e "s|^trust_height *=.*|trust_height = $TRUST_HEIGHT|" \
  -e "s|^trust_hash *=.*|trust_hash = \"$TRUST_HASH\"|" \
  "$LUMEN_HOME/config/config.toml"
```

State sync is not attempted when the home already has chain data. The
validator-kit state-sync helper is the automated equivalent and adds endpoint
agreement, validation, and safe update behavior.

## 5. Configure Cosmovisor and systemd

Validator-kit pins Cosmovisor to `v1.7.3`. The executable is separate from
the application layout: place the compatible `lumend` binary at
`$LUMEN_HOME/cosmovisor/genesis/bin/lumend` and reserve
`$LUMEN_HOME/cosmovisor/upgrades/` for upgrade directories.

```bash
export COSMOVISOR="/absolute/path/to/cosmovisor"
mkdir -p "$LUMEN_HOME/cosmovisor/genesis/bin" "$LUMEN_HOME/cosmovisor/upgrades"
cp "$LUMEND" "$LUMEN_HOME/cosmovisor/genesis/bin/lumend"
```

Create `/etc/systemd/system/lumend.service` with paths adjusted for the node:

```ini
[Unit]
Description=Lumen node (Cosmovisor)
After=network-online.target
Wants=network-online.target

[Service]
User=<node-user>
Environment=HOME=<node-user-home>
Environment=DAEMON_NAME=lumend
Environment=DAEMON_HOME=<LUMEN_HOME>
Environment=DAEMON_ALLOW_DOWNLOAD_BINARIES=false
Environment=DAEMON_RESTART_AFTER_UPGRADE=true
ExecStart=<cosmovisor-path> run start --home <LUMEN_HOME>
Restart=on-failure
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

Only unit installation and management require elevated privileges:
`sudo systemctl daemon-reload`, `sudo systemctl enable --now lumend`,
`systemctl status lumend`, and `journalctl -u lumend -f`. Verify RPC status,
P2P `net_info`, and `catching_up` manually before creating keys.

## 6. Create keys and register the validator

Use an encrypted local keyring and store its password and mnemonic offline.
The following mirrors the raw operations in
[`become_validator.sh`](../../scripts/blockchain/become_validator.sh):

```bash
export KEYRING_BACKEND="file"
export RPC="http://127.0.0.1:26657"
"$LUMEND" keys add validator --home "$LUMEN_HOME" --keyring-backend "$KEYRING_BACKEND"
ACCOUNT="$("$LUMEND" keys show validator -a --home "$LUMEN_HOME" --keyring-backend "$KEYRING_BACKEND")"
"$LUMEND" keys pqc-generate --name validator-pqc --home "$LUMEN_HOME" --keyring-backend "$KEYRING_BACKEND"
PUB_HEX="$("$LUMEND" keys pqc-show validator-pqc --home "$LUMEN_HOME" --keyring-backend "$KEYRING_BACKEND" | sed -n 's/.*PubKey (hex): *//p')"
```

Query `q pqc account "$ACCOUNT"`. If no association exists, submit and wait
for this transaction to commit:

```bash
"$LUMEND" tx pqc link-account --from validator --pubkey "$PUB_HEX" \
  --scheme dilithium3 --chain-id "$CHAIN_ID" --home "$LUMEN_HOME" \
  --keyring-backend "$KEYRING_BACKEND" --node "$RPC" \
  --yes --fees 0ulmn --broadcast-mode sync -o json
```

Obtain the consensus key and create a temporary validator definition. Replace
the placeholder amount with the intended self-delegation:

```bash
REAL_PUBKEY="$("$LUMEND" tendermint show-validator --home "$LUMEN_HOME")"
cat > /tmp/validator.json <<EOF
{
  "pubkey": $REAL_PUBKEY,
  "amount": "<SELF_DELEGATION>ulmn",
  "moniker": "${MONIKER:-lumen-validator}",
  "commission-rate": "0.1",
  "commission-max-rate": "0.2",
  "commission-max-change-rate": "0.01",
  "min-self-delegation": "1"
}
EOF
"$LUMEND" tx staking create-validator /tmp/validator.json \
  --from validator --chain-id "$CHAIN_ID" --home "$LUMEN_HOME" \
  --keyring-backend "$KEYRING_BACKEND" --node "$RPC" \
  --pqc-from "$ACCOUNT" --pqc-key validator-pqc --gas auto \
  --gas-adjustment 1.5 --yes --fees 0ulmn --broadcast-mode sync -o json
```

Query the transaction, `q staking validator`, and `q pqc account` before
delegating additional stake with `tx staking delegate`, `--pqc-from
"$ACCOUNT"`, and `--pqc-key validator-pqc`.

## 7. Recovery boundaries and automation mapping

Keep account/keyring material and the Dilithium private key separate from
consensus material. `priv_validator_key.json` signs blocks; its
`priv_validator_state.json` prevents double signing after recovery. The node
key identifies the P2P identity, while blockchain data and snapshots are
replaceable state. Recovery backups contain sensitive key/config material but
must not overwrite signing state blindly. Stop the service, preserve signing
state, and verify the target home before restoring.

| Manual operation | Validator Kit automation |
| --- | --- |
| Obtain and verify `lumend` | `scripts/install/download_lumend.sh` |
| Initialize and edit TOML | `./scripts/lumen-node deploy` and role profiles |
| Configure peers and seeds | deployment/network tooling |
| Derive state-sync trust | `./scripts/lumen-node state-sync` |
| Configure Cosmovisor | deploy/upgrade tooling |
| Write and manage systemd | `scripts/install/lumend_service.sh` |
| Health checks | `./scripts/lumen-node doctor` |
| PQC setup and validator registration | `scripts/blockchain/become_validator.sh` |
| Recovery export | `./scripts/lumen-node backup export` |
